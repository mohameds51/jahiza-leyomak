# جاهزة ليومك — صفحة الهبوط

صفحة هبوط عربية (RTL) لمنتج «جاهزة ليومك»: برنامج تجهيز العروس في آخر 30 يومًا قبل الزفاف، بسعر إطلاق 99 ريال سعودي (بدلًا من 199)، موجهة للسوق السعودي.

- **التقنية:** HTML + CSS + JavaScript بدون إطار عمل وبدون مكتبات ثقيلة. خطوة بناء صغيرة بـ Node فقط (بدون حزم). دالة خادم واحدة اختيارية (`api/lead.js`).
- **الوضع الافتراضي:** `TEST_MODE` — لا دفع ولا بيع ولا `Purchase`. أزرار الصفحة الرئيسية تقود إلى صفحة تسجيل قبل الإطلاق `/prelaunch`.
- **النشر:** GitHub → Vercel.

---

## 1. التشغيل محليًا

المطلوب: Node.js 20 أو أحدث.

```bash
cp .env.example .env.local      # عدّل القيم إن أردت (كلها اختيارية في TEST_MODE)
npm run dev                     # يبني ثم يشغّل http://localhost:4173
```

أوامر أخرى:

| الأمر | الوظيفة |
|---|---|
| `npm run build` | يبني `dist/` من `public/` ويحقن الإعدادات |
| `npm run serve` | يخدم `dist/` محليًا (مع روابط نظيفة و`/api/lead`) |
| `npm run check` | فحوصات ثابتة على `dist/`: روابط، ids، alt وأبعاد الصور، عبارات غير معتمدة، منع `Purchase` |
| `npm run test:api` | يختبر منطق `api/lead.js` (52 حالة) بقاعدة بيانات محاكاة، بدون شبكة |

لفحص الأحداث أثناء التطوير افتح الصفحة بـ `?jl_debug=1` وراقب `window.__jlEvents` ووحدة التحكم.

## 2. النشر على GitHub وVercel

```bash
git init
git add .
git commit -m "جاهزة ليومك: صفحة الهبوط"
git branch -M main
git remote add origin https://github.com/<حسابك>/<المستودع>.git
git push -u origin main
```

1. في Vercel: **Add New → Project** واستورد المستودع.
2. إعدادات البناء مضبوطة في `vercel.json` (Build: `node scripts/build.mjs` / Output: `dist`). اترك Framework Preset على **Other**.
3. أضف متغيرات البيئة (القسم 3). النشر الأول بدون أي متغير يعمل بوضع `TEST_MODE`.
4. اضغط **Deploy**.

> المعرّفات العامة (`SITE_MODE`, `META_PIXEL_ID`, `CLARITY_PROJECT_ID`, `LIVE_CHECKOUT_URL`, `LEAD_CAPTURE`…) تُحقن **وقت البناء**. أي تغيير فيها يتطلب **Redeploy**.

## 3. متغيرات البيئة

الملف النموذجي: `.env.example`.

| المتغير | عام/سري | الوصف |
|---|---|---|
| `SITE_MODE` | عام | `TEST_MODE` (افتراضي) أو `LIVE_MODE` |
| `LIVE_READY_CONFIRMED` | عام | يجب أن يكون `yes` حتى يُقبل `LIVE_MODE` |
| `LIVE_CHECKOUT_URL` | عام | رابط الدفع الحقيقي (`https://`). مطلوب في `LIVE_MODE` فقط |
| `META_PIXEL_ID` | عام | اتركه فارغًا لإيقاف Meta Pixel |
| `CLARITY_PROJECT_ID` | عام | اتركه فارغًا لإيقاف Clarity |
| `SITE_URL` | عام | رابط الموقع النهائي لوسوم المشاركة (OG) |
| `CTA_LABEL` | عام | نص الزر الرئيسي (افتراضي «ابدئي تجهيزاتك بـ99 ريال»، حتى 40 حرفًا) |
| `CTA_SHORT_LABEL` | عام | نص مختصر للترويسة والشريط الثابت (افتراضي «ابدئي الآن»، حتى 20 حرفًا) |
| `CONTACT_EMAIL` | عام | يظهر في صفحة الخصوصية إن وُضع |
| `LEAD_CAPTURE` | عام | `on` لحفظ تسجيلات `/prelaunch` (يحتاج `DATABASE_URL`). مع `off` (افتراضي) يظهر النموذج لكن الإرسال يعرض «التسجيل غير متاح حاليًا» |
| `DATABASE_URL` | **سري** | اتصال Neon. يُقرأ في `api/lead.js` فقط (الخادم) |

لا تضع أي سر في ملفات `public/`. لا توجد مفاتيح Paddle في المشروع حاليًا.

## 4. التبديل بين TEST_MODE وLIVE_MODE

| | `TEST_MODE` (افتراضي) | `LIVE_MODE` |
|---|---|---|
| أزرار CTA (7 أزرار) | تقود إلى `/prelaunch` ويُسجَّل `PurchaseIntent` | تقود إلى `LIVE_CHECKOUT_URL` ويُسجَّل `PurchaseIntent` ثم `InitiateCheckout` |
| صفحة `/prelaunch` | نموذج: الاسم الأول + البريد + واتساب (اختياري) ويُسجَّل `Lead` عند النجاح | تحوّل تلقائيًا إلى `/` |
| الدفع | لا يوجد، ولا يُحصَّل أي مبلغ | `LIVE_CHECKOUT_URL` |
| `Purchase` | لا يُسجَّل أبدًا | **لا يُسجَّل من المتصفح أبدًا** (انظر القسم 6) |
| فهرسة المحركات | ممنوعة (`noindex`) | مسموحة |

الصفحة الرئيسية **متطابقة** في الوضعين (لا رسائل تجريبية فيها). الفرق الوحيد وجهة الأزرار.

**للتفعيل:** اضبط في Vercel ثم Redeploy:

```
SITE_MODE=LIVE_MODE
LIVE_READY_CONFIRMED=yes
LIVE_CHECKOUT_URL=https://...
```

**الحماية:** البناء **يفشل عمدًا** إذا كان `SITE_MODE=LIVE_MODE` ولم يُضبط `LIVE_READY_CONFIRMED=yes` ورابط دفع `https://` صالح، فلا يمكن إطلاق وضع البيع بالخطأ.

### قائمة ما قبل LIVE_MODE (لا تكتب `yes` قبل إتمامها)

- [ ] الأدوات الخمس منفذة فعلًا وتعمل.
- [ ] التسليم مختبر من الدفع حتى وصول المشتركة للمنتج.
- [ ] حساب Paddle جاهز ومعتمد، ومنتج وسعر 99 ريال سعودي مُنشآن (تأكد من دعم Paddle لعملتك ومنتجك ودولة العميلة).
- [ ] رابط الدفع مختبر بعملية تجريبية.
- [ ] تنفيذ تتبع `Purchase` من الخادم (القسم 6).
- [ ] مراجعة النصوص: لا تضف ضمان استرجاع أو موعد تسليم أو وسائل دفع إلا بعد اعتمادها فعليًا.
- [ ] مراجعة قانونية لصفحة الخصوصية وإضافة الشروط والسياسات اللازمة.

## 5. إعداد التتبع

كل أدوات التتبع **اختيارية**، ولا تُحمَّل إلا بعد موافقة الزائرة. إذا تُركت المعرّفات فارغة لا يظهر شريط الموافقة ولا يُحمَّل أي سكربت خارجي (عدا الخطوط).

### Meta Pixel

1. Meta Events Manager → **Connect Data Sources → Web → Meta Pixel** وأنشئ Pixel.
2. انسخ **Pixel ID** (أرقام) وضعه في `META_PIXEL_ID` ثم Redeploy.
3. في إعدادات الـ Pixel **عطّل Automatic Advanced Matching** (الكود يطلب تعطيل الإعداد التلقائي، لكن راجعه من لوحة Meta أيضًا).
4. تحقق من **Test Events** في Events Manager (أو أداة Meta Pixel Helper) بعد قبول الموافقة في الصفحة.
5. **Custom Conversions:** `PurchaseIntent` حدث مخصص. لاستخدامه في تحسين الإعلان أنشئ Custom Conversion من Events Manager بقاعدة الحدث `PurchaseIntent`. كل الأحداث ترسل المعامل `site_mode` (`TEST_MODE` أو `LIVE_MODE`) لتفصل بين اختبارك وبيعك الفعلي.
6. راجع متطلبات Meta الحالية لتحقق النطاق (Domain Verification) وقياس الأحداث قبل تشغيل الإعلانات.

### Microsoft Clarity

1. أنشئ مشروعًا في Clarity، ثم **Settings → Overview** وانسخ **Project ID**.
2. ضعه في `CLARITY_PROJECT_ID` ثم Redeploy.
3. حقل البريد في النموذج مقنّع صراحة (`data-clarity-mask="True"`). يُفضَّل أيضًا ضبط وضع القناع (Masking) في Clarity على Balanced أو Strict.

### الأحداث

| الحدث | متى يُرسل | تكراره |
|---|---|---|
| `PageView` | تحميل الصفحة | مرة لكل تحميل |
| `ViewContent` | ظهور قسم الأدوات (تفاصيل المنتج) | مرة لكل جلسة |
| `PurchaseIntent` | الضغط على أي زر CTA | مرة لكل جلسة |
| `Lead` | **بعد نجاح مؤكد من الخادم** لتسجيل الاهتمام | مرة لكل جلسة |
| `InitiateCheckout` | `LIVE_MODE` فقط، عند الانتقال لرابط الدفع | مرة لكل جلسة |
| `Purchase` | **غير مفعّل من الواجهة** | — |

- لكل حدث `eventID` فريد (جاهز لإزالة التكرار لاحقًا مع Conversions API).
- `PurchaseIntent` و`Lead` ليسا مبيعات ولا يحملان قيمة مالية (`Lead` بلا `value` أصلًا).
- لا تُرسل أي بيانات شخصية (لا بريد ولا اسم) لأي أداة تحليلات.

### الخصوصية والموافقة

- الشريط يظهر عند أول زيارة. «لا أوافق» = لا يُحمَّل Pixel ولا Clarity.
- الأحداث قبل القرار تُحفظ في الذاكرة فقط وتُرسل عند الموافقة وتُحذف عند الرفض.
- زر «إعدادات التتبع» في التذييل يتيح تغيير القرار (سحب الموافقة يعيد تحميل الصفحة).
- صفحة `/privacy` تصف ما يفعله الكود فعليًا، لكنها **نموذج أولي يحتاج مراجعة قانونية** (نظام حماية البيانات الشخصية السعودي وغيره) قبل الإعلانات.
- الخطوط تُحمَّل من Google Fonts (تُذكر في صفحة الخصوصية). لخصوصية وسرعة أفضل يمكن استضافة خط Tajawal محليًا (ملفات woff2 داخل `public/fonts/`).

## 6. تتبع Purchase في LIVE_MODE (غير منفذ بعد)

القرار التصميمي: **المتصفح لا يرسل `Purchase` أبدًا** (لا بالوصول لصفحة شكر ولا بالضغط على زر). الكود يرفض ذلك صراحة، والفحص `npm run check` يفشل إذا ظهر.

المطلوب تطويره عند الإطلاق:

1. نقطة استقبال Webhook في الخادم من Paddle.
2. التحقق من **توقيع** الـ Webhook (سر Paddle في متغير بيئة خادم فقط).
3. التأكد أن حالة العملية «مدفوعة/مكتملة» حسب وثائق Paddle الحالية.
4. إرسال `Purchase` من الخادم (Meta Conversions API) مع قيمة وعملة فعليتين.
5. تسليم المنتج بعد التحقق.

لم أنشئ ملف Webhook وهميًا عمدًا حتى لا يوحي بأن الدفع يعمل.

## 7. التسجيل قبل الإطلاق `/prelaunch` (Neon PostgreSQL)

الصفحة تظهر دائمًا في `TEST_MODE`، لكن **لا يُحفظ شيء** حتى تضبط ما يلي (وإلا يعرض النموذج «التسجيل غير متاح حاليًا»):

1. أنشئ مشروع Neon ونفّذ `db/schema.sql` يدويًا في SQL Editor. إن كان الجدول موجودًا من نسخة سابقة (بريد فقط) فالملف يضيف عمودي `first_name` و`whatsapp` بأمان.
2. في Vercel أضف `DATABASE_URL` (متغير خادم عادي، **ليس** عامًا) و`LEAD_CAPTURE=on` ثم Redeploy.
3. شغّل `npm install` مرة واحدة وارفع `package-lock.json` (الحزمة `@neondatabase/serverless` بالوسم `latest`؛ ثبّت رقم نسخة بعد أول تثبيت ناجح).
4. أضف قاعدة **Rate Limiting** في Vercel Firewall على `/api/lead`.

ما تحفظه الدالة: البريد (حروف صغيرة)، الاسم الأول، الواتساب (اختياري، يُطبَّع: أرقام عربية هندية تتحول لإنجليزية وتُزال المسافات والشرطات)، وقت الموافقة، `utm_source`، `utm_campaign`. التسجيل المكرر بنفس البريد لا يستبدل السجل الأول. لا تُطبع بيانات شخصية في السجلات، ولا تذهب أي بيانات شخصية لـ Meta أو Clarity (وحقول النموذج مقنّعة في Clarity). لحذف سجل: `DELETE FROM leads WHERE email = '...';`

## 9. الجاهز وغير الجاهز

### جاهز ومختبر فعليًا
اختُبر في Chrome headless محليًا (Playwright) على أربع نسخ مبنية (افتراضية، تتبع، تسجيل، LIVE)، ومعه `npm run check` و`npm run test:api` (52/52). سكربتات المتصفح خارج المستودع ولم تُضف إليه. النتائج: 71 + 31 + 24 + 16 فحصًا ناجحًا.

- الأقسام وRTL، ولا تمرير أفقي عند 360 / 390 / 768 / 1280 بكسل في الرئيسية وصفحة التسجيل.
- جوال محاكى: CLS < 0.1، وLCP هو صورة الـ Hero، ولا أخطاء JavaScript، ولا ملفات مفقودة، وكل الأزرار ≥ 44px. زر الـ Hero الرئيسي ضمن أول شاشة (390×844) ونص الـ Hero في المنتصف.
- التباين: نص وصف الـ Hero 7.5:1 على أفتح نقطة في تدرج الخلفية (كان 4.45).
- الصفحة الرئيسية: لا عبارات «قيد التجهيز» ولا «تصوّر توضيحي» ولا «لا يوجد دفع»؛ السعر 99 ريال مع 199 مشطوبة بـ`<del>`؛ الشارات الثلاث؛ نص الزر الرئيسي؛ أسئلة الاستلام والضمان.
- كل أزرار CTA (7) تنقل إلى `/prelaunch` (اختُبر كل زر على حدة، وضغطة حقيقية على زر الـ Hero).
- `/prelaunch`: النصوص المطلوبة حرفيًا، إشعار «لن يتم تحصيل أي مبلغ» قبل النموذج، التحقق من الاسم/البريد/الواتساب/الموافقة، حقل الفخ، حالة التحميل ومنع الإرسال المزدوج، الفشل وإعادة المحاولة، انقطاع الشبكة، النجاح، وعدم استبدال سجل مكرر. مع `LEAD_CAPTURE=off` تظهر «غير متاح حاليًا» دون نجاح كاذب.
- التتبع: `PurchaseIntent` يُسجَّل قبل مغادرة الصفحة، و`Lead` فقط بعد نجاح مؤكد، ولا `Purchase` من المتصفح (حتى يدويًا من الكونسول)، ولا بيانات شخصية في طلبات Meta، ولكل حدث `eventID` فريد، ولا تكرار في الجلسة. قبل الموافقة/عند الرفض لا يُحمَّل Meta ولا Clarity.
- `LIVE_MODE`: كل الأزرار تقود لرابط الدفع، `PurchaseIntent` ثم `InitiateCheckout` (99 SAR)، `/prelaunch` يحوّل لـ`/`، وبوابة الأمان ترفض الإعدادات الناقصة.

### لم يُختبر بعد
اختبر هذه بنفسك قبل الإعلانات:

- **النشر الفعلي على Vercel** (بما فيه تشغيل `api/lead.js` كدالة هناك). المشروع اشتغل محليًا فقط.
- **الاتصال الفعلي بـ Neon**، وتثبيت `@neondatabase/serverless` (لم يتوفر تثبيت حزم أثناء التطوير، والاختبارات استخدمت قاعدة محاكاة).
- **Meta Pixel وClarity الحقيقيين.** اختُبر منطق التحميل والأحداث بسكربتات بديلة، لا بخوادم Meta/Clarity. تحقق من Test Events في Meta بعد النشر.
- **Paddle** ورابط الدفع الحقيقي. في اختبار `LIVE_MODE` استُخدم رابط وهمي.
- **سرعة الصفحة الفعلية** (Lighthouse / PageSpeed على الإنترنت الحقيقي). لم تُشغَّل أي أداة قياس درجات.
- **أجهزة جوال حقيقية وSafari وiOS.** الاختبار كان على Chrome فقط.
- **خط Tajawal الفعلي من Google Fonts.** كان محجوبًا أثناء الاختبار، فالمعاينة البصرية تمت بخط احتياطي، وقد يختلف الشكل قليلًا. راجع الصفحة بعد النشر.

### يحتاج إعدادًا منك
- `META_PIXEL_ID` و`CLARITY_PROJECT_ID`، `SITE_URL`، `CONTACT_EMAIL`.
- Neon و`DATABASE_URL` إن أردت تفعيل تسجيل الاهتمام.
- تثبيت نسخة `@neondatabase/serverless` بعد أول `npm install`.
- قاعدة Rate Limiting في Vercel.

### يحتاج تطويرًا قبل البيع
- الأدوات الخمس نفسها (الصفحة تصف المنتج المخطط فقط).
- ربط Paddle وتتبع `Purchase` من الخادم والتسليم (القسم 6). الصفحة تعد بـ«الاستلام بعد الدفع مباشرة»، فلا تفعّل `LIVE_MODE` قبل أن يعمل التسليم فعليًا.
- صفحة سياسة استرجاع تطابق «ضمان استرجاع لمدة 14 يومًا» (التزام فعلي تجاه العميلة).
- مراجعة قانونية لصفحة الخصوصية، والشروط وسياسة الاسترجاع إن وُجدت.
- (اختياري) استضافة الخط محليًا.

### نقاط تحتاج قرارك
- **سعر 199 المشطوب** يجب أن يكون سعرًا حقيقيًا ستبيعين به لاحقًا، وإلا فهو مخاطرة على قبول إعلانات Meta ومن ناحية حماية المستهلك.
- **«جاهز خلال 3 أيام»** وعد زمني متحرك؛ عدّليه إن تأخر. ومن تسجل الآن يجب أن تحصل فعلًا على سعر 99.
- **الصور الخمس** تُظهر عناصر لم تُذكر في وصف المنتج (مثل «تنبيهات بالمهام الأساسية» و«ترشيحات للمنتجات» و«اختيار الفستان»). أزيلت عبارات «تصوّر توضيحي» بطلبك، فتأكدي أن الأدوات النهائية تطابق الصور قبل الإعلانات.
